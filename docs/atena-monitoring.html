Watching Atena

Three checks that answer three different questions about the website assistant, so that the first person to notice she has stopped answering is never a visitor.

Service novieri-chat Host HubSpot app function Origin www.novieri.com Owner Novieri S.A.S.

What actually breaks

Atena is a HubSpot serverless function that calls a model provider and answers from a profile generated out of the site's own copy. Five things go wrong, and only one of them is visible without instrumentation.

FailureWhat a visitor seesDetectable by
API key missing or revokedError notice in the widgetHealth check · deep check
Provider outage or credit exhaustedError notice in the widgetDeep check only
Provider rate-limits the accountSome get answers, some get the errorDeep check · in-function alert
Bad deploy removes the endpointError notice in the widgetHealth check only
Handoff fails to reach the CRMNothing. A warm goodbye and the WhatsApp number.In-function alert only

The one worth building for

The last row is the expensive one. When a visitor asks for a person, Atena hands over the Colombian WhatsApp line and the server posts the transcript to the CRM. That delivery is deliberately fail-open — no CRM error is allowed to break a reply — so when it fails the conversation still ends perfectly and nobody at Novieri learns the lead exists. They arrive on WhatsApp saying "hola" and everything they explained is gone.

No external monitor can see this. It is reported from inside the function, which is why the site-side alerting and the ops-platform checks below are complements, not alternatives.

Tier 1 · Health

Is the machine assembled?

no model call

Confirms the function is deployed, its secrets are present and the HubDB store it depends on answers. Costs nothing per run, so poll it as often as the platform likes.

     "rate_limit_table":true, "store_reachable":true}}

Verdict: status 200 is up, 503 is down, anything else — including a timeout, a 404, or HTML instead of JSON — is down and means the deploy removed the endpoint. Do not parse the body to decide; the status code carries the verdict on its own.

Assertion ladder

Run in order. The first failure is the verdict, and the rung that failed is the diagnosis.

  1. A response arrived before the timeout. No → down, unreachable.
  2. Status is 429. Yes → up, and stop. That is Novieri's own rate limiter working, not an outage.
  3. Status is 200. No → down; record the status and the error field.
  4. The body parses as JSON and has no error key. No → down.
  5. reply is a string of at least 20 characters. No → down; an empty reply reaches the visitor as an error.
  6. reply matches /barranquilla/i. No → degraded: she answered but not from her own profile, which is how a broken content build shows up.

Rung 2 is the one monitors get wrong. Treating 429 as an outage produces alerts caused by the monitor itself.

Tier 3 · Handoff

Does a lead actually arrive?

writes to the CRM — weekly, never hourly

Asks to speak to a person, then confirms a ticket carrying that transcript exists in the CRM within two minutes. It is the only check that covers the silent failure, and the only one that leaves a trace in real business data.

CadenceWeekly
Window120 s
Markerin the message
Cleanuprequired
  • Send a message that asks for a human and carries a unique marker, e.g. ops-probe-2026-08-17, so the resulting ticket is identifiable.
  • Poll the CRM tickets search for that marker. CRM search is not read-your-writes — it lags by tens of seconds. Poll for up to two minutes before declaring failure; a single immediate query will report a false outage.
  • Close or delete the ticket afterwards. A monitor that leaves debris in the support queue gets muted by the humans who work it.
  • Alert as critical on failure. This one is silently losing customers.

The rate-limit budget

The chat endpoint defends itself, and a monitor is indistinguishable from a visitor. These limits are per calling IP unless noted, and they cap how often Tier 2 can run.

BucketLimitWindowEffect on a monitor
chat_burst560 sNo practical effect
chat2015 minNo practical effect
chat_day6024 hThe binding constraint
chat_all (site-wide)80024 hShared with real visitors

Do the arithmetic before choosing a cadence

A 5-minute Tier 2 cadence is 288 runs a day against a 60-a-day ceiling. The monitor would exhaust its own quota before 10am and spend the rest of the day measuring nothing but its own 429s — while reporting up, because rung 2 says a 429 is healthy. Silent blindness, dressed as green.

30 minutes = 48 runs a day and fits under the cap with room. Tighter than that needs one of: a raised CHAT_DAILY_PER_IP for the monitor's address, or a probe bypass header that skips rate limiting and nothing else. Ask before assuming either exists.

Alerting

Severity should follow how many people are affected and whether anyone else would notice, not how alarming the error text looks.

ConditionSeverityFires afterReasoning
Tier 1 failscritical2 consecutiveThe endpoint is gone; every visitor is affected
Tier 2 failscritical2 consecutive~60 min of silent failure at a 30-min cadence
Tier 2 degraded (rung 6)warning3 consecutiveShe answers; the content build is suspect
Tier 2 latency > 12 swarning3 consecutiveThe function is killed at 15 s — this is the cliff edge
Tier 3 failscritical1Leads are being lost invisibly

Two consecutive failures rather than one, because a single provider hiccup is not an incident and a monitor that cries wolf gets ignored — except Tier 3, which runs weekly and whose failure mode is already silent.

Deduplicate against the site's own alerts. The function opens a CRM ticket on failure, capped at one per kind per hour. During a real outage the ops platform and that ticket describe the same event. Correlate on a five-minute window rather than paging twice.

Every run, whatever the verdict — the history is what turns "it broke" into "it has been degrading since Tuesday".

A defensible first objective: 99% of Tier 2 runs return up over a rolling 30 days, with p95 latency under 10 seconds. Both are measurable from the fields above and neither requires the provider's cooperation.

Notes for whoever implements this

  • The Origin header is mandatory on Tier 2. Without it the function replies 403, which means "bad client", not "service down" — the most likely way this integration fails on its first day.
  • Never store an API key for this. Tier 1 and Tier 2 need no credentials at all. Only Tier 3 needs CRM read access, and only to search for its own marker.
  • Latency is the leading indicator. The provider gets slow before it fails, and the function is killed at 15 seconds. A run creeping from 5 s to 12 s is a warning that has not become an outage yet.
  • Do not let probe traffic reach the analytics. Tier 2 conversations are real conversations to any counter watching. Tag or exclude them or the numbers drift.
  • Keep the question in sync with the site. Rung 6 asserts a fact from the generated profile. If Novieri ever moves cities, this check fails before anyone notices why — which is arguably correct, but only if the runbook says so.
  • Reference implementation: scripts/check-atena.mjs in the website repository implements Tier 2 exactly as specified, exits 0 or 1, and prints --json shaped for ingestion. Port it, or shell out to it.
